# Service records and infrastructure ports

[COMPONENTS](COMPONENTS.md) owns package dependencies; [IR-CONTRACTS](../02-domain/IR-CONTRACTS.md) owns canonical data; [DEVELOPMENT-PLAN](../11-roadmap/DEVELOPMENT-PLAN.md) names the planned Go methods. This document fixes the shared operational records so adjacent tasks do not invent incompatible handles.

## Common request context

Every mutation receives project ID, operation/request ID, idempotency key, expected project revision, captured configuration/plan/target/corpus/policy hashes where applicable, and cancellation context. Trusted actor/channel/lease owner derive from constructor/session state. Client parameters cannot overwrite them. Idempotency hashes exclude transport request IDs but include all semantic input/subject fields.

## Ports and deterministic injection

- Repository provides transaction-scoped project/detection/baseline/approval/IR/case/plan/run/mission/event operations, expected-revision compare-and-swap, and same-project/reference validation. Only the SQLite implementation accepts raw database handles internally.
- ArtifactStore provides sanitized Put, registered Get, entity Link, Verify and reconciliation. Byte writes precede SQLite metadata; immutable evidence stays reachable.
- AdapterRegistry holds resolved, integrity-validated bindings keyed by unique adapter ID/version, and exposes only admitted source/target ports. It rejects missing/duplicate registrations. It remains constructor-owned immutable configuration, not a package discovery index; execution still checks current qualification, gates and captured subjects. Package resolution supplies configuration, never framework rules or authority.
- Runner accepts a fixed ToolSpec (`executable_id`, argument array, safe working root, explicit env secret refs, timeout/output limits, sandbox handle), returns exit/capture/cleanup evidence, and never accepts a shell string from an agent.
- Clock supplies UTC `Now() time.Time`; IDGenerator supplies `NewID(prefix string) string`. Tests inject fixed/advanced clocks and deterministic unique IDs. Wall time never substitutes for event sequence or a fencing token.

Source/target ports are defined in SYSTEM-DESIGN. Their operations are invoked only through gate-checked services. Construction resolves credentials at execution into memory and redacts them before persistence; no repository API writes plaintext secrets.

## Result publication

A producer stages immutable result artifacts, captures all parent hashes and its live fence, then CompareAndPublish checks the current revision/subjects/ownership and commits projection plus event links. Failed publication returns a stale/conflict error with preserved diagnostic refs. A previous idempotent result is historical unless its subjects remain current.

Cross-record semantic checks cover duplicate IDs, local-ID/baseline resolution, ownership, gate parents, rule/case coverage, DAG order, fixture reset identity, target path/before hashes and lease expiry. JSON Schema validates structure; these service rules validate meaning.

## Execution records and injected ports

`ExecutionEvent`, `ExecutionState`, `ProgressMetric` and `ExecutionPage` map to `specs/execution/`. Events identify execution operation/run, stage instance, task/mission/entity, reason/result, captured subjects, refs and sequence. `ExecutionSink` validates/redacts append requests and participates in the domain transaction for state-changing completion/control/approval events. `ExecutionReader` reads current state at N plus event page through M ≤ N; it cannot claim historical projection; it cannot mutate gates, start work or acknowledge alerts globally.

`internal/execution` derives control mode from persisted control events, checks active run/fence/captured subjects, validates numerator/denominator/basis/accounting revisions and emits bounded liveness. Domain service constructors inject these ports; runners expose enough lifecycle/control information to heartbeat during slow work and checkpoint safely. Explanations are deterministic factual templates with attributed evidence-backed proposals, not prompt or chain-of-thought storage. Existing operation IDs serve as execution run IDs; verifier runs remain separate entities.

Current durable service records map to v2 approval/resolution/model/decision/profile/causality/attestation/scope/validity schemas. Process-private handles do not replace these records. Supervisor/resource ownership and fenced writes follow RECOVERY; serial project mutation is the initial revision model.

## Shared assessment checkpoint services

`assess`/`assessment.run` coordinate existing guarded analysis/observation/behavior/feasibility services with a selected scope; no assessment analyzer, new adapter port or duplicate IR is introduced. A failed/unsupported evidence-acquisition dimension creates a diagnostic finding and may still publish a useful COMPLETED assessment operation/report. Storage/event failure that prevents durable publication cannot report completion. `assessment show`/`assessment.get` read immutable assessed-state projection plus separately evaluated current validity. They do not synthesize a plan or execute source code.

`assessment decide` derives trusted human action metadata and persists immutable selection, index and event atomically with project revision checks; it never writes user_confirmations or implementation missions. Omitted nullable/list decision input fields become explicit null/empty values in the engine-produced selection; CONTINUE_PLANNING requires exact selected scope and intent. Imports, assessment refs and linked analysis/dependency/evidence resolve under the same project/secret controls. A current explicit CONTINUE_PLANNING selection is an additional prerequisite of `plan`/`migration.plan`, not Gate 2 itself. Planning publishes its immutable assessment delta/reuse witnesses and hashes selection+basis refs in the exact PLAN subject. Semantic checks enforce same project, report/selection/basis equality, latest effective human continuation, current source/target/scope and compatible chosen units. An assessment result or selection alone never satisfies unit admission.

## Exact implementation qualification

An advertised capabilities/supported_profiles entry is descriptive metadata, never sufficient admission authority. For the initial subset, the registry accepts only an exact input profile/implementation/schema tuple backed by a current engine-derived qualification record. `specs/adapters/qualification.schema.json` names implementation and schema refs, capabilities, exact input_profile_ref, approved control_suite_ref, observed control_result_refs, limitations, status and reason codes. No manifest back-reference is needed, so manifest→qualification→binary/profile/control closure is acyclic. Qualification publication uses trusted test/control execution and ordinary fence/provenance validation; imported agent status=SUPPORTED cannot establish support. The control suite declares required positive and deliberate-negative outcomes; the service derives SUPPORTED only from matching complete results with no in-scope limitation. Structural validation alone cannot establish these facts.

The execution manifest is owned by CONFIRMATION-PROTOCOL and pins the installed deterministic engine/schema/build bytes; adapter manifest 2.1/2.2 pins consumed schema/qualification refs. A planned adapter may advertise future profiles with empty qualification refs but is never admitted. An implemented adapter with only unit tests cannot claim an untested runtime profile. Repeating a qualified exact profile retains that profile's residual limitations; no inferred widening of version ranges. A generic executable constraint/profile language and broader capability lattice are DEFERRED prerequisites of M8, not hidden authority in open supported_profiles JSON.

Current publication requirements: attestation 2.1 for acceptance; qualified data-model 2.0 for DB lowering; benchmark 2.2 plus the Gate-2-bound performance policy for current performance claims. Old structural branches are historical readers, not fallback admission. Semantic checks resolve profile/schema refs, same-project ownership, IDs/column arity, applicable capabilities and control outcomes; an empty evidence array or claimed latest version cannot satisfy them.

Qualification does not introduce a Gate-1 cycle. Before source approval, installed engine/detection/extraction capabilities are qualified using reviewed synthetic controls and exact intended profiles without running the customer's application. Gate 1 only binds those initial capabilities. Source runtime controls/attestations run afterward in an approved disposable environment and qualify observation dimensions before acceptance. PLAN pins all subsequently consumed probe/runner/comparator qualifications. An unqualified runtime may yield unavailable assessment findings; initial source confirmation never authorizes assuming it is complete. No qualification record references the future subject that consumes it.

## Framework-skill composition using existing ports

## Executable adapter binding

**Status: SPECIFIED; invocation/loading implementation and runtime qualification pending.** [SKILL-SPEC](../06-agent/SKILL-SPEC.md) owns discovery/resolution. Existing adapter manifest 2.2 adds `binding` and `operations` without replacing the manifest or AdapterRegistry. Branch 2.2 covers SOURCE/TARGET only; PROBE/RUNNER/COMPARATOR retain their existing explicit registrations. Manifest 2.1 may execute only through an explicit built-in registration matching its exact implementation bytes; it cannot imply an external command. Older branches remain historical. PLANNED 2.2 has binding=null and no callable operations. IMPLEMENTED metadata alone proves neither executable availability nor qualification.

Each operation descriptor uniquely names one existing operation and exact request/result schema-byte refs, timeout_ms and max_response_bytes. SOURCE supports Detect, Parse, Extract, PrepareInstrumentation; TARGET supports ValidateCapabilities, Generate, PrepareHarness. Duplicated operations or schema refs absent from manifest.schema_refs are invalid. No port is inferred from a capability tag. Missing required operations refuse affected execution with ERR_UNSUPPORTED_CAPABILITY. PROBE/RUNNER/COMPARATOR retain their current role-specific registrations; external protocol 1 is deliberately limited to SOURCE/TARGET.

| Binding | Resolution and invocation |
| --- | --- |
| BUILTIN | factory_id selects an explicit constructor in the existing composition root. Registration must match exact manifest ID/version/direction and implementation_ref, not merely factory name. Factory exposes the declared ports and operation schemas. Unknown factory is unavailable. |
| EXTERNAL | protocol=rwt-adapter-stdio-1; implementation_ref equals executable_ref and identifies one separately distributed native executable's raw bytes. executable_path is a relative regular-file location inside its verified immutable installation root, never a shell string/PATH lookup. Engine verifies content immediately before launch, pins the opened file or immutable installation against replacement, and uses Runner with an empty argument array. Dependent libraries/platform/runtime and any required asset closure are pinned by the exact input profile/control environment; an interpreter/script wrapper is outside protocol 1. |

The external protocol bridges the same ports; it is not another plugin system or service. Per invocation the existing Runner starts one process in the approved sandbox, sends one UTF-8 JSON REQUEST conforming to [invocation.schema.json](../../specs/adapters/invocation.schema.json), closes stdin, and requires one JSON RESPONSE followed by process exit. There is no persistent daemon, handshake, session continuation or unsolicited output. Duplicate JSON keys, invalid UTF-8, extra non-whitespace stdout, mismatched request/project/operation/manifest/implementation echo, nonzero exit or absent response are protocol failures, never successful output. Request/response use rwt-cjson-1 lexical limits, no BOM, with a maximum 64 KiB request envelope and the declared response-byte limit. stderr is bounded sanitized diagnostics, not evidence or protocol. No caller-provided command/argv or ambient credentials enter the protocol.

input_ref names immutable registered operation input bytes validated against request_schema_ref. The existing port table owns required semantic inputs/results: private process handles cannot be serialized as arbitrary addresses, paths or secrets. Every external operation must have a qualified concrete input/result schema translating only its approved artifact/profile/staging capabilities; if no such schema/bridge exists, that operation is unavailable. The engine mounts only its verified input closure read-only and a fresh owned output/staging directory; no approval tokens, unrestricted host paths or measured-state checker writes. Fixed input/output mount names are /rwt/input and /rwt/output inside the sandbox. An input artifact is available as /rwt/input/<64-hex-digest>, and an emitted artifact as /rwt/output/<64-hex-digest>; engine validates the raw digest, bounded closure, schema, ownership, redaction and paths before importing/publication. Registered input dependencies use the same layout; private source/environment attachments remain subject to their role-specific admission. Symlinks/special files and output references outside the granted closure are refused. Generation may write only its granted disposable target staging tree. PrepareHarness returns a fixed Runner specification; it does not start measured applications itself.

An OK response requires output_ref and error=null; ERROR requires output_ref=null and a structured code/optional sanitized diagnostic_ref. Local codes use ERR_UNSUPPORTED_CAPABILITY, ERR_INVALID_CONTRACT or ERR_INTERNAL from ERROR-CATALOG; publication retains existing domain errors. An adapter's OK means only that a proposed port result exists: engine validates it and derives current state/qualification/verdict independently. Untrusted statuses cannot grant PASS, completeness or approval. Returned refs must resolve imported verified output or preexisting granted input, not invented evidence.

Engine starts the deadline before launch, applies the descriptor timeout and existing Runner quotas, and on cancellation/timeout/limit/protocol failure terminates owned subprocesses and performs RECOVERY cleanup. No implicit retry: preserve diagnostics and partial staged refs; retry only under the owning operation's idempotency/reset/fence rules. Timeout→ERR_TIMEOUT, cancellation→ERR_CANCELLED, corrupt bytes→ERR_ARTIFACT_CORRUPT, malformed wire/result→ERR_INVALID_CONTRACT, unavailable binding/profile→ERR_UNSUPPORTED_CAPABILITY. No completion or acceptance may publish before successful exit, output verification and current-subject/fence checks. Disk/event failure follows existing emergency persistence rules.

Registry construction can validate bindings without executing customer code. Qualification controls invoke reviewed synthetic inputs before customer admission; subsequent use retains normal Gate 1/2 requirements. Unsupported loading protocol or operation cannot become executable by package installation. Implementation may initially expose only built-in ports; external availability is claimed only after X40 binding controls execute. No M0/M1 prerequisite or boundary is expanded by this specification.

## Exact composed-profile qualification

[composition-profile.schema.json](../../specs/adapters/composition-profile.schema.json) is an immutable **input profile artifact**, not a registry or qualification mechanism. It names source/target package descriptor refs; exact source/target adapter manifests, implementation bytes, individual input profiles and qualification refs; a target-model 2.1 specimen; all nonprimitive TIM lowering qualification refs; PROBE/RUNNER/COMPARATOR provider tuples; and exact corpus, comparison policy and environment profile refs. source_package_content_ref/target_package_content_ref resolve the canonical package inventories, whose package.json entries resolve source_package_ref/target_package_ref respectively; verify all consumed file digests per SKILL-SPEC. There is no reliance on mutable discovery metadata. Lists are sorted by direction/adapter_id/adapter_version/manifest_ref for providers and raw digest bytes for lowering refs; duplicate provider tuples are refused.

The composed qualification remains qualification 1.0: subject_kind=ENGINE, implementation_ref equals the tested engine binary, input_profile_ref equals this composition artifact, schema_refs names every consumed schema, and capability_ids names the tested composition obligations. Engine derives status from the ordinary positive/negative control suite and actual result refs. There is no COMPOSITION status or self-issued skill qualification. Adapter manifests reference only individual adapter qualifications, never this downstream composition qualification; the profile and its target model cannot reference the composed result or future approval. This keeps the closure acyclic.

Admission resolves each individual qualification and checks same project, direction, implementation/profile/schema/capability equality, current validity and accepted controls. Source/target package adapter refs must match their provider tuples. tim_model_ref must resolve the tested target model; every nonprimitive lowering's exact qualification is present, with provider/shape/obligation identity validated by TARGET-ARCHITECTURE. Every required observation/comparison mechanism has an independently qualified provider; merely having one of each verification role is insufficient. The composed corpus/policy/environment must equal the tested scope, not a wider customer claim. Changed composition requires new controls; individual support alone cannot imply combined support.

Approval uses existing fields: bind exact adapter manifests/implementation refs in adapter_bindings; include composition profile, composed qualification and consumed package descriptors/tree-evidence refs in PLAN decision_refs. Pin schema and input-profile closure through existing execution/adapter manifests. SOURCE has no decision_refs: its existing rewrotron-engine binding resolves execution-manifest 1.1, whose package_refs pins descriptor/content inventory pairs whenever packages are consumed. PLAN uses the same execution closure plus the composition decision_refs. Package-free built-in execution retains execution-manifest 1.0. Validate these typed refs before approval/admission; canonical subject version/preimage is unchanged. Composition-control artifacts reference tested inputs only, not future customer subjects. Missing/stale qualifications block executable planning while assessment may still complete with findings. Profile qualification does not authorize implementation or certify generated customer output.

Publication order is implementation/assets + schemas + individual input profiles → individual controls/qualifications → adapter manifests → package descriptors/inventories → composition profile → ENGINE composed controls/qualification → approval closure. Individual qualification inputs cannot reference the final package inventory or consuming adapter manifest; pin examined asset bytes separately to avoid package→manifest→qualification→package cycles. Verification provider tuples resolve directional adapter manifests, not the consuming engine execution manifest. Qualification publication rejects cycles and future-result refs.

Execution-manifest 1.1 package_refs is sorted by content_ref then descriptor_ref; descriptor/inventory hashes must match each other, consumed files and the frozen package identity. Reject two different contents for the same consumed package ID/version. Engine/build qualification precedes the consuming execution manifest; do not include that manifest in its own qualification input.
