# Project lifecycle and readiness

**Owner:** Durable lifecycle transitions. [CONFIRMATION-PROTOCOL](CONFIRMATION-PROTOCOL.md) owns exact subjects and gate checks, not display stage percentages.

INITIALIZED → DETECTED → SOURCE_CONFIRMED → ANALYZED → MODELED → PLAN_SYNTHESIZED → PLAN_CONFIRMED → MIGRATING → VERIFIED → BENCHMARKED → READY_CUTOVER. These are the storage CHECK enum. OBSERVE/VERIFY/REPAIR/FINALIZE are display stages, not new durable lifecycle values. Pause/failure/packaging completion are execution state/outcomes, not extra projects.status values. Repeated observe/model/repair cycles are allowed with current subjects; lifecycle advancement is engine-validated, never agent-declared.

Gate 1 requires coherent snapshot and reviewed detection/assertions. Deep work binds that snapshot. Gate 2 requires an executable, feasible in-scope plan, exact resolution and immutable target/decision/model refs. Unit completion uses UNIT plus applicable implemented regressions; it does not move the whole project to VERIFIED. VERIFIED requires current PROJECT acceptance. BENCHMARKED requires required accepted performance evidence (or explicitly approved non-applicable workload/dimensions); absence cannot pass. READY_CUTOVER requires current Gates 1/2, PROJECT acceptance, accepted performance, session/data/rollback rehearsal, complete release evidence and Gate 3. Execution COMPLETED denotes approved packaging, not actual production deployment.

Drift invalidates current applicable states and approvals while keeping history. Source changes require successor coherent baseline/Gate 1; target/policy/corpus/choice changes require successor plan/Gate 2. Implementation-only edits preserve Gate 2 but remove current verification/benchmark/release. Resume checks subjects, bytes, versions, leases/processes/journals, user pause and validity; conversation history is unnecessary. No historical result/status creates current readiness.
