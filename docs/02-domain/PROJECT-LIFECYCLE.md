# Project lifecycle and readiness

**Owner:** Durable lifecycle transitions. [CONFIRMATION-PROTOCOL](CONFIRMATION-PROTOCOL.md) owns exact subjects and gate checks, not display stage percentages.

INITIALIZED → DETECTED → SOURCE_CONFIRMED → ANALYZED → MODELED → PLAN_SYNTHESIZED → PLAN_CONFIRMED → MIGRATING → VERIFIED → BENCHMARKED → READY_CUTOVER. These are the storage CHECK enum. OBSERVE/VERIFY/REPAIR/FINALIZE are display stages, not new durable lifecycle values. Pause/failure/packaging completion are execution state/outcomes, not extra projects.status values. Repeated observe/model/repair cycles are allowed with current subjects; lifecycle advancement is engine-validated, never agent-declared.

Gate 1 requires coherent snapshot and reviewed detection/assertions. Deep work binds that snapshot. Gate 2 requires an executable, feasible in-scope plan, exact resolution and immutable target/decision/model refs. Unit completion uses UNIT plus applicable implemented regressions; it does not move the whole project to VERIFIED. VERIFIED requires current PROJECT acceptance. BENCHMARKED requires required accepted performance evidence (or explicitly approved non-applicable workload/dimensions); absence cannot pass. READY_CUTOVER requires current Gates 1/2, PROJECT acceptance, accepted performance, session/data/rollback rehearsal, complete release evidence and Gate 3. Release-operation COMPLETED denotes approved packaging, not actual production deployment; other operation kinds complete their own scoped outputs. Assessment-operation completion is defined below and implies neither release readiness nor verified migration.

Drift invalidates current applicable states and approvals while keeping history. Source changes require successor coherent baseline/Gate 1; target/policy/corpus/choice changes invalidate affected findings and any existing plan/Gate 2; a successor plan/Gate 2 is required only for renewed implementation, not assessment-only reporting. Implementation-only edits preserve Gate 2 but remove current verification/benchmark/release. Resume checks subjects, bytes, versions, leases/processes/journals, user pause and validity; conversation history is unnecessary. No historical result/status creates current readiness.

## Assessment checkpoint in the shared workflow

This document is the canonical owner of assessment completion, reports and continuation. There is one domain progression:

```text
source → assessment → assessment report → explicit user decision
       → executable plan → explicit Gate 2 approval → implementation → verification
```

Assessment reuses snapshot/detection, source/dependency analysis, observation, behavior modeling and feasibility services. It is a checkpoint/projection of those services, not a second migration pipeline, adapter interface or analysis engine. A project may successfully stop here. These progression labels do not add states to the storage lifecycle CHECK enum above.

### Inputs, boundary and safe execution

Inputs are the coherent source snapshot, detected environment and separate assertions, available dependencies, requested target intent, critical workflows, constraints/business requirements, and available observations/evidence. Missing optional evidence is an assessed gap, not an excuse to manufacture it. Assessment never requires an exact feasible target, complete Behavior IR, approved corpus or executable plan. Source characterization can remain partial. Static-only findings do not establish runtime behavior.

`assess` requires Gate 1 for deep analysis; it delegates to the existing guarded services under the selected assessment scope/profile. Runtime observation is optional and runs only on disposable independent environments with the existing effect/capture controls. Missing runtime, unsafe replay, unsupported adapter or unresolved dependency produces findings and a completed report where persistence succeeds. Assessment never changes original source, production state or target code. Source/detection summaries before Gate 1 are not deep assessment; report rendering cannot bypass Gate 1 to gather evidence. Read-only access to an already persisted assessment does not require current migration approval.

### Completion and report identity

Assessment status (COMPLETED for a published report) is distinct from migration/project lifecycle status and plan completion. A successful assessment means the best supported assessment of the declared scope and currently available evidence has been persisted. It is not a claim of adequate coverage, viability, bounded effort or future success. Feasibility can be VIABLE (no material blocker found within examined evidence/scope), VIABLE_WITH_CONDITIONS (named prerequisites/changes remain), PARTIALLY_UNDERSTOOD (some scope has support while material gaps remain), BLOCKED (a known unmet prerequisite prevents selected work) or UNKNOWN (evidence cannot support a feasibility conclusion). None certifies migration success. BLOCKED/UNKNOWN feasibility is a successful assessment outcome, not an operation failure. Cancellation, corruption or inability to persist a report remains a failed/cancelled operation; never report completion without durable bytes.

[assessment-report.schema.json](../../specs/reports/assessment-report.schema.json) defines the immutable assessed-state projection at `as_of_sequence`, with exact input/analysis refs. This is a captured report, not a promise to reconstruct arbitrary historical mutable state. Its findings retain the underlying canonical analysis record identities; assessment and migration use those same records. The report includes system summary, examined scope, evidence/limitations, changes and reasons, dependency strategies, compatibility, risks/blockers, alternatives, unknown/unsupported behavior, missing evidence, suggested characterization/work sequence, assumptions and uncertainty. Effort estimates require supporting evidence and bounded scope; null means not estimable, never zero effort. Each material finding is OBSERVED, INFERRED, UNKNOWN, UNSUPPORTED or RECOMMENDED, has provenance, and names its static/runtime/user/mixed basis. Static-only findings must state limitations. Missing evidence has a reason/diagnostic provenance, never fabricated observation.

Published reports are immutable artifacts indexed in SQLite. Current assessment views ([assessment-view.schema.json](../../specs/reports/assessment-view.schema.json)) separately expose report identity, whether it is latest, current validity and per-finding validity/evidence. Historical reports remain retrievable when migration is blocked or inputs change. A report is not a migration plan, approval receipt, PASS, proof of equivalence or implementation permission. Rendering Markdown/JSON produces views of the same report identity.

### Explicit user decision and optional continuation

After a report the engine waits. Assessment-only execution stops with no implementation missions, target publication or automatic plan/generation. A human may STOP, REQUEST_EVIDENCE, CHANGE_TARGET, CHANGE_SCOPE, SELECT_WORK, ACCEPT_RECOMMENDATIONS, REJECT_RECOMMENDATIONS or CONTINUE_PLANNING. The immutable [assessment-selection.schema.json](../../specs/project/assessment-selection.schema.json) records the exact report, selected scope/intent, findings, dependency/recommendation proposal refs and human action. It is a progression decision, not a fourth approval gate. Changing configuration remains a separate explicit user edit; selection cannot silently rewrite it. Accepting a recommendation records intent to use it, not verification or activated implementation authority.

Human local `assessment decide` persists the selection under the same-account trust boundary. Agent-readable CLI/MCP cannot infer this choice from report generation, silence, a selected UI control or conversation history. MCP agents retrieve the report and request the human local decision; no assessment tool issues approval tokens. Only an explicit CONTINUE_PLANNING selection with a selected work scope permits executable planning; SELECT_WORK alone records scope without continuing. No implementation is authorized by either. Selecting continuation does not automatically run the planner: `plan`/`migration.plan` is a separate explicit operation, resolving the supplied or current persisted selection. A STOP supersedes current continuation; later continuation needs a successor selection. Human pause/`continue` only controls process scheduling and cannot create this decision.

### Planning, reuse and invalidation

The planner validates the selection against current project inputs, derives a version 2.1 plan envelope from the assessed findings and selected scope, and binds an immutable [assessment-planning-basis.schema.json](../../specs/migration/assessment-planning-basis.schema.json). The basis identifies changes since assessment, still-valid reused findings, stale findings and new work/evidence. Exact target resolution, dependency choices, executable contracts/corpus and prerequisites must be ready for the selected scope; assessment completion alone cannot meet those requirements. In-scope unresolved blockers prevent an executable plan, but do not destroy or fail the assessment report. Out-of-scope findings remain visible rather than disappearing from historical evidence.

The PLAN approval subject remains version 2.0: its existing `decision_refs` includes both the human selection and planning-basis artifact refs. The immutable reference closure binds the report, selected scope and delta without rewriting historical subject bytes or introducing circular approval references. Version 2.1 plan envelopes expose `assessment_ref`, `selection_ref` and `planning_basis_ref`; services enforce equality with the hashed selection/basis closure, current source/intent/scope and ordered units. Old plan envelopes remain readable history; a legacy plan lacking this checkpoint must be re-planned and explicitly approved before current execution. Assessment hashes are never accepted as Gate 2 subject hashes or authorization tokens.

Changes to source/snapshot, intent, environment, dependencies/decisions, adapters, policies, evidence or other inputs propagate through the [typed validity graph](DOMAIN-MODEL.md). Each finding names its actual prerequisites; target-independent source facts do not acquire target edges merely because the report also assesses a target. Unknown impact is conservatively stale. Report history survives; unchanged findings may be reused only after engine evaluation of their dependency predicates and witnesses. A planning-basis record captures those checks even before a plan exists; it is not a plan-to-plan reuse certificate and cannot reuse an old verification PASS. Reused analysis retains the original record/ref, with current validity witnesses, rather than running a separate assessment analyzer. New evidence produces successor reports/graphs/selections/plans as applicable. Any affected plan subject change requires Gate 2 again; unrelated completed work is retained under the canonical reuse rules.

### Required falsification evidence

[TESTING](../10-development/TESTING.md) X41–X55 defines the fifteen assessment acceptance experiments. Structural schemas do not prove non-mutation, reuse or authorization enforcement. No assessment runtime capability is advertised until those applicable experiments execute.

Hash closure must remain acyclic: a report references the pre-publication graph of input/finding ancestors, not a graph that hashes that same report. Later graph revisions can index published reports/selections; a planning basis similarly references its existing prerequisite graph, with downstream plan edges published in a successor graph. Current views use those successor graphs. Reports/bases cannot include their own future hash.

Report cross-record validation resolves each analysis/provenance/input ref in the project, checks reported classification against the evidence kind and declared dimension, and accounts for each material scoped finding. OBSERVED with STATIC_ONLY means an observed source/configuration fact, never observed runtime behavior; INFERRED/RECOMMENDED cannot establish truth. Suggested sequence references existing findings with unique ordered positions; estimate bounds require lower ≤ upper and supporting scope/method evidence. Current views must cover every report finding exactly once, and `as_of_sequence` cannot exceed the view current sequence. A non-latest report can still have valid findings; latest is not a freshness guarantee. Report/selection/plan wrapper IDs and refs are checked for exact closure equality rather than trusting displayed fields.

Assessment and selected-work `scope_ref` resolve [work-scope.schema.json](../../specs/project/work-scope.schema.json), a shared pre-plan input, not a verification acceptance scope. It records snapshot, included source/entrypoint boundaries, critical workflow/constraint/business requirement refs, operational profile, exclusions and limitations. It requires no executable cases or corpus. An empty known entrypoint list is allowed before discovery; selected source paths identify the sealed boundary. Assessment or selected scope cannot escape that snapshot. The planner lowers chosen work to separate UNIT/PROJECT acceptance scopes once cases exist, explicitly describing expansions/reductions and new assessment work in its basis. Unknown business requirements remain unknown; scope descriptors are not executable behavior semantics.

Selection actions have explicit subjects: SELECT_WORK/CHANGE_SCOPE require selected_scope_ref, CHANGE_TARGET requires a user-owned intent ref, ACCEPT/REJECT_RECOMMENDATIONS name at least one report finding, and REQUEST_EVIDENCE names the requested evidence. Referenced recommendation findings/proposals and selected scope must resolve in the reviewed report or be explicitly identified as expanded/unassessed work. Other omitted selection fields become null/empty, never an implicit choice. Aggregate current report validity is STALE if any required input/finding is stale, otherwise UNKNOWN if any required predicate cannot be established, otherwise VALID; valid findings require witnesses. This applicability result is not a verification PASS or assessment coverage claim.
