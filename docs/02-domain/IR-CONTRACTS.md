# IR identities, provenance and compatibility

**Owner:** Three-tier neutral records. Source/Application/Behavior IR remain distinct; target choices belong to [TARGET-ARCHITECTURE](../04-migration/TARGET-ARCHITECTURE.md). Source IR describes syntax/calls/files; Application IR describes entrypoints/components/data/workflows; Behavior IR describes executable obligations and uncertainty.

IR identities bind project, immutable configuration/source snapshot and schema version. Schema 1 IR envelopes can reference v2 contracts/cases/workflows; their envelope version does not upgrade those records. IDs are stable document-local IDs; persistent records use baseline/plan-qualified version IDs. All refs resolve to same-project registered artifacts and exact bytes. Evidence kinds STATIC, RUNTIME, USER_OVERRIDE and AGENT_PROPOSAL remain distinct; an agent proposal cannot establish capture, DEAD or PASS.

Source records retain file bytes/content hashes, syntax status, source spans, symbols/edges and unresolved expressions. Parser-specific ASTs are private auxiliary data, never required core node vocabulary. Current reference symbol vocabulary is a supported subset, not universal completeness: a language construct not faithfully representable yields an UNSUPPORTED finding and inhibits closure. Broader adapters must first add versioned neutral facets with loss-preservation fixtures, not map incompatible declarations to PHP categories silently.

Application entrypoints include HTTP, CLI, cron and event; each type has relevant bindings, dispatch precedence, profile and evidence. Streams/WebSockets require a later explicit capability. Operations can have multiple entrypoints; workflow bindings/branches use v2 [BEHAVIOR-MODEL](BEHAVIOR-MODEL.md), not a linear-only list. Data/effect identity includes connection/catalog/schema/table or named state store.

Behavior IR preserves contract/case/scenario refs, executable operators, pre/post/invariants, actor/state/effect relationships, async boundaries and unknowns. Descriptive v1 business_rules.data is not interpreted. Current generation accepts only v2 typed semantics supported by both evaluator and target capabilities. Unsupported operators/schema versions, invalid IDs, contradictory routes, unresolved required evidence or unbounded workflow paths block; no fallback evaluator.

Every IR transition preserves source/evidence links, identity relations, causal order/transaction boundaries, raw input distinctions, environment/profile, uncertainty and capability gaps. Confidence is an estimate with methodology, never proof. Required-field/schema changes create immutable successor artifacts and dependent invalidation. Legacy v1 descriptive documents remain inspectable; they do not satisfy current execution merely because they validate structurally.

Current data models use data-model.schema version 2.0 with connection/catalog/schema qualification and exact server behavior evidence, owned by DATABASE-COMPARISON. Adapter manifests 2.1 (explicit built-in) / 2.2 (package-callable) pin schema bytes and qualification refs; execution manifests pin the core interpreter/build/schema closure. Logical schema URIs name contracts but do not freeze their bytes. Missing pinned bytes or unsupported qualification blocks execution, while historical artifacts remain readable under their retained schemas.

## Capture identity and interpretation preservation

Source-only ledgers are observation identities, not verification correspondence. A source observation/context/effect has no dependency on target values or a future case; derived maps/reports reference immutable captures downstream. Preserve actor partition, session epoch, qualified resource, original value, occurrence and trusted capture provenance at all IR transitions. File initialization/top-level effects are application entry/initialization nodes; unsupported initialization remains unresolved, never discarded as declaration-free dead content. Broader non-HTTP invocation envelopes and language-specific detection facets remain M8 prerequisites; HTTP response/status is a named current capability, not a universal application law.

## Source/target skill composition

[SKILL-SPEC](../06-agent/SKILL-SPEC.md) packages deterministic adapters without changing these three IR layers. Source conventions end at evidence-backed neutral records; target-specific organization belongs in TIM/provider lowering. Never encode a source→target recipe as canonical application meaning. Reactive state, native navigation or offline synchronization are future qualification candidates: lacking a faithful versioned facet produces UNSUPPORTED/UNKNOWN, not HTTP flattening or implicit target code. X40/M8 tests source-independent obligation preservation and incompatible lowerings.
