# Behavior model and bounded executable semantics

**Owner:** Behavior meanings, executable vocabulary and scenario semantics. [IR-CONTRACTS](IR-CONTRACTS.md) owns identities/provenance; schemas under specs/behavior define shape. Current executable contract/case/scenario records are v2; v1 DECLARATIVE open JSON is historical/descriptive and not an executable rule language.

## Claim terminology

| Term | Establishment |
| --- | --- |
| Observed equivalence | Named observations match under the approved profile/policy; no claim about unseen inputs |
| Contract equivalence | All required assertions/cases in an identified acceptance scope pass with sufficient capture |
| Semantic equivalence | Equivalent under explicitly named semantics and an applicable demonstrated comparator/proof method; not inferred universally from finite cases |
| Unverified behavior | Specified/reachable behavior without current applicable verification |
| Unknown behavior | Insufficient/conflicting evidence or missing semantics/capture |
| Unsupported behavior | Named mechanism/operator/protocol lacks declared implementation capability |
| Intentional change | Human-approved explicit policy/contract difference; separately displayed, never an accidental mismatch masked by a waiver |

PASS/MISMATCH/UNKNOWN remain the three verdicts. UNSUPPORTED and BLOCKED are capability/readiness reasons, not extra successful verdicts. Unsupported in-scope behavior yields UNKNOWN and blocks scoped acceptance. Known violations yield MISMATCH even when other dimensions are UNKNOWN; either blocks. Successful cases do not establish corpus completeness.

## Interpreter vocabulary

[semantics.schema.json](../../specs/behavior/semantics.schema.json) is a closed tagged language, never PHP, SQL, shell or arbitrary expressions. Limits: depth 32, at most 1,000 expression nodes per contract, 100 actions/branches/array elements and 100 executed scenario steps. Limit violations return ERR_UNSUPPORTED_CAPABILITY with node/operator/limit. No dynamic evaluator or unrestricted extension code.

Values: UTF-8 string, boolean, exact integer/decimal represented as canonical decimal strings, null, RFC3339 timestamp instant, bytes by registered ref, typed object and ordered array. Absent reference is MISSING, distinct from null, empty string, zero and false. Reference namespaces are input, actor, state, result, clock, binding and row, with JSON Pointer and declared type. Wrong type or absent required binding produces UNKNOWN/ERR_UNBOUND_VALUE; it cannot quietly take an else branch. No implicit PHP/Python/JS truthiness/coercion.

Operators: literal/ref; eq with equal declared types (decimals compare exact numeric value); lt/lte for same numeric or string type (strings byte order); before/at_or_before for timestamp instants; in tests typed array membership; and/or/not require boolean operands; exists/is_missing/is_null inspect references; add/sub exact numeric same-type arithmetic; array/object construct values; coerce permits only INTEGER_TO_DECIMAL and CANONICAL_STRING_TO_INTEGER. Integer range is signed 64-bit for executable arithmetic; larger transport IDs remain exact strings and are not coerced. Decimal arithmetic preserves exact rational base-10 values with max 38 coefficient digits and 18 fractional digits after exact normalization (as defined in EVALUATION-CONTEXT); exceeding limits returns unsupported, never rounds. Unsupported operators fail schema validation; capability mismatch after valid parsing blocks execution.

An ordered branch chooses the first true boolean guard; last guard must be literal true unless exhaustive disjointness is established by a supported deterministic check. Unknown earlier guard yields UNKNOWN, not fall-through. Actions: assert, set_state, bounded db_read, db_write, begin/commit/rollback, emit, session, respond, error. The role matrix below governs their execution; effectful actions operate only in shadow simulation or generated application code, never measured-state checking. DB actions are connection/catalog/table-qualified and translated only through discovered safe identifiers and typed ports, never raw user SQL. The initial shadow simulator/generated action subset supports one active transaction per connection; nested/distributed transactions are unsupported. begin/commit/rollback IDs must pair; error/exit outcomes define rollback behavior explicitly.

Preconditions run before actions, postconditions at the declared completion boundary, invariants before/after each state transition. Authorization uses explicit actor/state predicates, including negative wrong-principal cases; descriptive authorization text cannot substitute for a predicate. Business decisions involving time use controlled clock/reference predicates, never broad timestamp masking. Emit records effect class, destination, payload and idempotency relationship; the runner enforces safety independently.

## Scenarios and async boundaries

[workflow.schema.json](../../specs/behavior/workflow.schema.json) v2 identifies actors/principal fixtures, initial state, environment/profile, inputs, guarded steps, bindings, transition edges, terminal success/failure/unsupported states, expected effects and bounded execution. Each step names its actor, operation and immutable request. Bindings evaluate before request execution against the preceding committed observations; each names value expression, exact selector and PERCENT_ENCODED/HEADER_VALUE/JSON_VALUE encoding. A selector into raw_target names an explicit `{binding-name}` template marker, a header selector indexes its ordered record, and body_json selector is a JSON Pointer into a declared JSON body. Only declared sites may change; header CR/LF is rejected, percent encoding uses UTF-8 RFC3986 component escaping, and JSON_VALUE preserves typed exact scalar values. Conflicting selectors, undeclared markers, non-JSON body transformation or unavailable observations block. Persist effective request bytes separately; unbound base requests retain original bytes. In the current v2 subset, step.guard is reserved and must be exactly {"op":"literal","value_type":"boolean","value":true}. Reaching a step dispatches it once; there is no implicit skip state. Reject false/nonliteral step guards before dispatch with ERR_UNSUPPORTED_CAPABILITY (unsupported conditional step); a missing required guard is ERR_INVALID_CONTRACT; schema rejection is an admission failure, not an observed application MISMATCH. Conditional routing uses the ordered transition guards after the step completion boundary. Only transition lists require a final explicit fallback guard or supported deterministic exhaustiveness evidence. False transition guards advance to the next transition; an evaluated UNKNOWN stops without selecting a fallback. Exactly one next_step_id or terminal_id is non-null. IDs resolve, all planned paths are bounded, and a path exceeding max_executed_steps is unsupported, never successful truncation. The first subset permits an acyclic finite graph or explicitly unrolled paths; unbounded loops/concurrency/streams are rejected.

Observation scenarios carry inputs only and reference a workflow/profile; they cannot assert invented legacy outcomes. Verification cases add reviewed assertions and source evidence. Separate role/account/inventory/payment/feature/time outcomes are explicit paths or separate cases, never flattened into one happy path. Each side maintains its own cookie jars and workflow state; actors cannot share a jar unintentionally.

Completion modes: PROCESS_EXIT, HTTP_RESPONSE for demonstrably synchronous scope, or SINK_ACK_QUIESCENCE with the acknowledged-logical-effect threshold, predicate, timeout and positive quiescence duration defined below. Queue dispatch is not delivery; sink acceptance and worker acknowledgement are separate evidence. Timeout, late uncorrelated effect or missing receipt yields UNKNOWN/MISMATCH as appropriate. General eventual-consistency proofs and arbitrary distributed schedules are deferred.

## Evidence obligations

Every contract/branch/assertion links source evidence and open uncertainty. [Runtime observation](../03-analysis/RUNTIME-OBSERVATION.md) supplies mechanism attestations; [compatibility](../05-verification/COMPATIBILITY-SPEC.md) supplies relation-preserving comparisons. Fixtures, corpus partitions and comparator mutation tests require independent review, so one agent cannot create both a flawed oracle and its own certificate. Unsupported semantics stay explicit in Behavior IR and feasibility; they are not discarded during target lowering.

## Deterministic evaluation and DB action subset

The following are interpreter requirements, not claims of an existing implementation. Pin the interpreter binary and schema bytes through the execution manifest in CONFIRMATION-PROTOCOL. New row/bind capabilities require qualification; a structurally valid record cannot activate an unsupported operator.

Boolean guards, assertions, preconditions, postconditions and invariants must evaluate to boolean. Evaluate and/or operands left-to-right with short circuit: false ends and, true ends or. An evaluated missing/wrong-type operand yields UNKNOWN, never false; an unvisited operand is not evaluated. exists/is_missing/is_null accept reference operands only: exists(null)=true, is_missing(null)=false, is_null(null)=true; for MISSING the answers are false/true/false. Other operators on MISSING yield ERR_UNBOUND_VALUE. Type checking precedes execution even for unreachable actions; unsupported constructs cannot hide in an unselected branch.

JSON Pointers follow RFC6901, including ~0/~1 decoding; invalid escapes, negative indices and noncanonical array indices are rejected. Reading an absent member returns MISSING. set_state writes only an existing declared state slot with matching type; it cannot create intermediate objects, mutate actor/input or change a fixture schema. Bindings are single-assignment within an operation; duplicate names are rejected before execution. Objects compare key sets and typed values recursively, arrays compare ordered typed elements; cross-type equality is unsupported. Timestamp equality/order compares instants, not spelling. Integer arithmetic checks signed-64 overflow. Decimal literals accept the schema's exact decimal spelling, then evaluate as coefficient/scale with trailing fractional zeros removed (zero loses its sign); no binary float or rounding. The 38-digit/18-fractional limit applies to exact evaluated results. Stored artifact spellings remain unchanged for hashing.

`row` exists only while evaluating a discovered table's candidate-row predicate or UPDATE value; elsewhere its use is ERR_UNBOUND_VALUE. db_read evaluates a boolean where per candidate row and binds an ordered typed-row array. max_rows is a hard evidence bound: an extra qualifying row makes the result unsupported/incomplete, rather than truncating it into an acceptance oracle. Initial order_by names discovered columns in ascending order using the pinned database semantics; arbitrary expressions, descending/mixed ordering, joins and aggregation are unsupported. Empty order_by does not license sorting an otherwise order-sensitive observation.

INSERT requires where=literal true and emits one row from typed values; UPDATE/DELETE evaluate where against each pre-write row. UPDATE values are evaluated against that same pre-write row and applied together; empty UPDATE is unsupported. DELETE requires empty values. Initial support is bounded single-row insertion and explicitly bounded row mutations through typed ports; unsupported engine coercion, complex generated values or an unbounded mutation blocks. db_write's optional bind names a result containing affected_rows, returned_rows and generated_values. Returned rows carry discovered model types; generated_values is keyed by discovered generated columns. A missing generated value remains unavailable, never guessed from sequence arithmetic or another connection's last ID. Generated application ports must qualify safe same-connection retrieval; simulator bindings are explicitly shadow values. Actual verification bindings use independently captured inserted-row evidence and maintain response/foreign-key/effect relations; ambiguous retrieval yields UNKNOWN.

Every DB action resolves connection/catalog/table to exactly one current qualified data model; ambiguity, including same table in multiple schemas, blocks this initial action subset. A write's transaction_id must match the live transaction on that connection, or null for explicit autocommit. respond/error terminates the operation and skips subsequent actions. Neither implicitly commits nor rolls back. A terminal action with an open transaction is unsupported; declare commit/rollback before it. Runner failure cleanup rolls back/abandons owned environments but cannot be asserted as application behavior. Assert failure interrupts actions and blocks acceptance; application error outcomes need an explicit error branch and reviewed postconditions.

HTTP_RESPONSE/PROCESS_EXIT require zero receipts and zero quiescence; their synchronous boundary must be demonstrated. SINK_ACK_QUIESCENCE requires positive quiescence, the causal logical-effect counter below and a boolean completion predicate. An established duplicate business application is MISMATCH; transport retry receipts require the typed delivery comparison below. Unavailable capture or undetermined late effect is UNKNOWN. Only declared success/error terminal postconditions run after their completion boundary; unmet preconditions do not manufacture an application failure result. General transactional languages, implicit coercion, distributed transactions and unbounded temporal logic remain unsupported.

## Execution roles (normative)

| Role | Permitted | Prohibited |
| --- | --- | --- |
| Fixture preparer / scenario driver | Restore approved initial fixtures before measurement, attest reset, supply declared inputs, bind identities from actual preceding captures, advance bounded occurrences | Applying expected writes/effects, modifying measured state after the boundary, forcing a successful branch |
| Model simulator | Interpret db_write/db_read/emit/set_state/transaction/response actions in isolated shadow state to derive expectations | Connections to measured stores, sink delivery, exporting simulated values as observations |
| Application runner | Launch witnessed source/target and deliver driver inputs | Hidden expected-model setup, substituting another executable |
| Observer | Capture actual effects through qualified independent channels | Declaring correctness or injecting expected effects |
| Assertion evaluator | Resolve immutable ACTUAL_OBSERVED context, evaluate approved obligations and correspondence | Store mutation, expectation fallback, asserting fixture label is principal evidence |
| Comparator / verdict engine | Derive scoped verdict from approved rules, actual observations and evaluated obligations | Application repair, evidence creation, corpus edits, broadening normalization |
| Generator | Lower obligations into owned target components | Certifying generated code as verified |

Fixture preparation, simulation, measurement and evaluation have distinct provenance classes: FIXTURE_PREPARED, MODEL_EXPECTED, ACTUAL_OBSERVED; expected effects carry MODEL_EXPECTED, actual effects ACTUAL_OBSERVED. Shadow state is a different allocation/store with no measured-store handle or credentials. Simulation may start from a copied fixture, but never aliases its live state. The app alone causes measured writes. Runtime control X61 audits all checker principals and store/sink writes: a missing INSERT must remain absent and MISMATCH. Violation of separation invalidates the attempt; it cannot PASS.

Earlier DB action descriptions specify generation/shadow-model semantics. Their write-result bindings contain shadow values in simulation; actual assertion bindings come solely from measured effect/context records. set_state is shadow-only. During checking, model writes/emits/transactions are expected obligations, never executed store commands. Preconditions/assertions read phase-qualified contexts. Model assertions cannot create actual result/error/row values. An application error is observed behavior; an evaluator type error is UNKNOWN with a machine reason.

[Evaluation context](EVALUATION-CONTEXT.md) v1 owns namespace shapes, phase availability and exact projection. [Differential testing](../05-verification/DIFFERENTIAL-TESTING.md) owns logical occurrence and branch pairing.

## Supported HTTP response and session lowering

The respond action optionally supplies ordered typed headers, typed cookies and redirect_location; omitted lists mean empty model obligations, not framework defaults. Location may be supplied through redirect_location or one Location header, never both. Redirect status is 301/302/303/307/308; preserve method progression through declared workflow steps. Headers preserve repeated field occurrences; names compare ASCII case-insensitively, values/order under the approved policy. Set-Cookie cannot be put in the generic header action: use cookies, one field per cookie, preserving duplicate names with distinct path/domain. Never fold cookies with commas.

Cookies specify name, value expression, nullable domain/path/max_age/expires/same_site, secure, http_only. Null attributes mean absent, never inferred defaults. Exact expiry/lifecycle relations survive normalization. Header/cookie values reject CR/LF and unsupported bytes. A session action declares CREATE/ROTATE/UPDATE/INVALIDATE, principal expression (null for anonymous), previous/current side-local references, typed value expressions and whether previous identity must become unusable. Simulation changes shadow sessions; generator lowers through a pinned qualified provider; observer independently captures actual continuity/rotation/invalidation. UUID/hash/password/template computation beyond the primitive vocabulary uses a named pinned lowering capability with input/output obligations and qualification refs in Target Implementation Model. No arbitrary provider expression operator is introduced. Missing actual principal/session evidence yields UNKNOWN, not the intended fixture identity.

HTTP_RESPONSE and short quiescence establish only the declared synchronous/bounded window. A required effect scheduled outside that window is UNSUPPORTED/UNKNOWN until a separate bounded schedule experiment is approved. Queue state and declared horizon must be inspected; finite silence never proves unbounded absence. Duplicate receipts alone are not necessarily duplicate business effects; COMPATIBILITY-SPEC owns delivery semantics.

Initial typed response projection preserves generic-header order and cookie order separately; Set-Cookie fields project only into the cookie list, while raw trace evidence retains wire ordering. If a contract requires interleaving order between Set-Cookie and other fields, this initial lowering cannot express that obligation and must return an explicit capability gap. Do not silently discard that required order. Literal/model expression array limits and context capture row limits are different: observed DB rows use the qualified profile/db_read max_rows bound; oversized contexts are incomplete, never silently truncated.

## Bounded completion counter and clock (B4)

The canonical completion record is semantics.schema.json#/$defs/completion, shared by model/workflow records and the observation profile's completion_ref. The profile ref must resolve to a registered artifact of this exact shape/qualified schema. The profile supplies the default completion and maximum timeout; an explicit workflow step completion governs that occurrence and may use another mode only with the profile's qualified capture/queue capabilities. Its timeout cannot exceed the profile timeout. Unsupported mode or excessive timeout blocks admission; different login/create modes do not require separate workflows. This is a completion boundary, not a verification verdict.

For SINK_ACK_QUIESCENCE, expected_receipts is a **minimum number of distinct acknowledged logical effects**, not physical receipts, attempts, rows or business applications. Count each (side, initiating step occurrence, logical_effect_id, destination_id) at most once. Require causal links, the same typed business key/payload relationship, a durable APPLIED acceptance, and an ACKNOWLEDGED record with non-null receipt_id/ack_id/business_application_id referring to that acceptance. A retry may supply the ACK through DEDUPLICATED acceptance of the same business_application_id; it adds no count. Rejected, requested-only, unacknowledged or unproven outcomes contribute zero; missing required capture yields UNKNOWN, never an assumed count. Actual records alone establish the counter; simulator expectations cannot contribute. COMPATIBILITY-SPEC independently checks exact business-effect cardinality: exceeding the minimum cannot excuse a duplicate or unexpected effect.

Use controlled monotonic elapsed time, zero at the witnessed operation dispatch. The initial single-supervisor capture records event timestamps from one monotonic clock, anchored once to a recorded UTC dispatch epoch; elapsed_ms is the integer millisecond offset from that epoch; round activity offsets upward and timer reads downward at sub-millisecond boundaries so rounding cannot shorten the required quiet interval. Integer-clock fixtures need no rounding. Do not subtract worker wall-clock timestamps or use the business clock namespace. effect-occurrence.elapsed_ms stores the observed offset relative to its step_occurrence_ref. The optional field has no implicit zero; its absence prevents timed completion, while retaining readable untimed evidence. Each scoped activity must have qualified timing from the same initiating dispatch anchor; for delivery records this is elapsed_ms, and other capture channels must expose equivalent offsets in their pinned capture evidence. Clock/capture qualification must establish that projection; without it completion is UNKNOWN. timeout_ms is the fixed deadline; retries/activity never extend it. quiescence_ms must be positive and at most timeout_ms for async mode (service cross-field check). HTTP_RESPONSE/PROCESS_EXIT require expected_receipts=0 and quiescence_ms=0. Async zero threshold is permitted for a reviewed absence obligation; it still requires positive capture/queue evidence and the predicate, never inference from silence.

Eligibility requires the initiating invocation's admitted HTTP response/process exit to have been captured, counter >= expected_receipts, predicate evaluating TRUE in the current actual context, sufficient required capture and inspected queue state with no pending in-window work. UNKNOWN predicate/capture cannot establish eligibility. Start the quiescence clock when eligibility first holds. Reset it on any scoped actual delivery attempt, receipt, acknowledgement, queue change or other captured effect, even a deduplicated retry; loss of eligibility clears it. Re-entering eligibility starts a new clock. Process activity before timer checks at the same timestamp. Completion occurs at the earliest instant with continuous eligibility and no scoped activity for quiescence_ms, at or before the fixed deadline; equality is allowed. Evaluate deadline failure after a qualifying timer at that instant. On timeout with no established violation, return UNKNOWN/incomplete completion. A known branch/effect/assertion violation remains MISMATCH and cannot be erased by timeout. Completed boundaries are immutable; subsequently discovered in-scope late effects invalidate current result use rather than editing history.

For async completion, the schedule horizon is timeout_ms from dispatch; measurement runs through the admitted completion or timeout, and queue inspection must cover work due within that horizon. For proven synchronous modes, schedule_horizon_ms is zero; scheduling required work beyond it is UNSUPPORTED/UNKNOWN. No claim of unbounded future absence is made. X07/X72 and [contract-blocker-vectors.json](../../specs/examples/contract-blocker-vectors.json) specify retry counts, ACK loss, deadline equality and timer reset controls; actual sink/worker tests remain implementation validation.
