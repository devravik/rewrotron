# Confirmation protocol and canonical approval subjects

**Owner:** All gate identities, preimages, human authorization and invalidation. Current subjects use schema version 2.0 and [approval-subject.schema.json](../../specs/project/approval-subject.schema.json). Old v1 artifacts remain readable historical evidence, never inferred current approvals.

| Gate | Exact subject | Authorizes |
| --- | --- | --- |
| GATE_1_SOURCE_DETECTION | SOURCE subject/configuration_hash | Analysis, isolated observation, modeling and planning against sealed source |
| GATE_2_PLAN_CONFIRMED | PLAN subject/plan_hash | Generation, controlled publication, repair and sandbox verification |
| GATE_3_CUTOVER | RELEASE subject/release_hash | Approved release package/runbook; no initial production execution |

## Hash preimage v2

Subjects are immutable registered artifacts. SOURCE binds sealed snapshot, detection, separate human assertions and exact source/probe bindings. PLAN binds configuration_hash, snapshot, Behavior IR, corpus, policy, user intent, exact resolution, target model, immutable decision refs, validity graph, all adapter/runner/comparator bindings, consumed skill/tool/knowledge revisions, ordered units, dependency edges, omission proofs, exclusions and blockers. RELEASE binds configuration/plan, target tree, whole-project report, accepted benchmark (or the exact approved not-applicable performance policy under PERFORMANCE), runbook and rollback rehearsal. Schema-required null is distinct from absent; optional absent fields have no implicit hash default. All relevant choices must be explicit before hashing. Proposal refs are not confirmation refs: normalization and dependency decisions are approved transitively by the plan, avoiding circular hashes.

`subject_hash = SHA256(rwt-cjson-1(subject))`, represented as 64 lowercase hex. Neither subject_hash, timestamps, actor, mutable progress, approval receipt nor registry lookups are part of this preimage. Nested refs hash exact artifact bytes; the same hash under another project does not confer ownership. Execution requires registered same-project/transitively authorized refs, size/hash/schema verification and available pinned implementations. A digest alone cannot prove bytes exist or are trusted.

## rwt-cjson-1 serialization

UTF-8 JSON, no BOM or trailing newline, no whitespace outside strings. Recursively order object keys by their unnormalized UTF-8 byte sequence. Preserve Unicode code points; reject invalid surrogate code points, duplicate keys and non-finite/floating numbers. Values are objects, arrays, strings, signed 64-bit integers, booleans or null. Integers use shortest decimal, no leading zeros or negative zero. Strings escape quote/backslash and U+0000–001F using JSON short escapes for backspace/tab/newline/formfeed/carriage return and lowercase `\u00xx` otherwise; do not escape slash or non-ASCII. Arrays retain schema-defined semantic order.

Set-valued refs/IDs sort lexicographically by UTF-8 bytes and reject duplicates before serialization. adapter_bindings sort `(role,adapter_id,version,manifest_ref,implementation_ref)`. Dependency edges sort `(prerequisite_id,dependent_id)`. ordered_units use deterministic topological order: among ready units highest priority then unit_id bytes; cycles block. Unit case_ids, contract_refs and capabilities are sets. Omission/exclusion/decision/revision refs are sets. A supplied noncanonical set/order is rejected, not silently reinterpreted during approval.

[approval-hash-vectors.json](../../specs/examples/approval-hash-vectors.json) contains preimages, canonical bytes and expected digests. Structural Python checks are not proof the eventual Go canonicalizer passes. Implementations must reproduce vectors, shuffled object key cases, non-ASCII/escape/null cases and rejected duplicate/float/invalid-order cases.

## Reconstruction and upgrades

Load the original subject bytes and its complete immutable reference closure from SQLite/artifacts; validate using its retained schema/canonicalizer version. Never rebuild from the current adapter registry, latest locks or generated YAML. Store approved payload ref, schema/canonicalization version, hash and receipts. Upgrading engine/adapters does not rewrite historical subjects. A missing old executable/schema prevents executing/rechecking that subject; it does not alter what was approved. A successor execution plan names new versions and requires Gate 2. No migration may manufacture approvals for upgraded subjects.

## Human channel and tokens

Confirmation is an append-only user_confirmations record, not inferred silence/conversation or a YAML flag. Local CLI `confirm source/plan/cutover` requires explicit exact subject hash and trusted human context. `approval issue` locally issues a short-lived, one-use token bound to project, gate, exact subject, human context and expiration; MCP confirmation tools consume it transactionally. Agents cannot issue tokens through MCP, supply their own human identity or turn DECIDED/APPROVAL_RECEIVED events into receipts. Same-account CLI use remains a trust boundary, not OS isolation. Dry-run never creates token/receipt.

Idempotent retries return the existing receipt; different payload under the same key conflicts. Confirmation, reviewed payload, receipt/event and current validity change commit atomically. Validate current parents, availability, feasibility and subjects immediately before commit. Explicit overrides are immutable human assertions alongside measured facts; contradictions with doctor measurements remain findings, not falsified detection.

## Invalidation

Live customer drift prompts a successor coherent snapshot and Gate 1; previously sealed snapshot/history remain intact. Target intent, dependency strategy, corpus, comparator, normalization, lowering/ownership choice or consumed execution revision changes invalidate affected current PLAN/Gate 2 and Gate 3; renewed implementation requires successor PLAN/Gate 2, while assessment-only use can remain stopped. Implementation-only code changes within approved choices retain Gate 2 but invalidate results/release. [DOMAIN-MODEL](DOMAIN-MODEL.md) owns typed selective reuse; unknown impact invalidates conservatively. Progress/heartbeats never change an approval hash. Gate 3 requires current whole-project PASS, no in-scope unresolved blocking UNKNOWN/MISMATCH, required accepted performance and rollback/session evidence. Percent progress is never readiness.

## Assessment is not authorization

The shared [assessment checkpoint](PROJECT-LIFECYCLE.md) can complete without feasible executable planning. Source approval still gates deep characterization. The human continuation selection is a separate progression record, never user_confirmations, an approval token or a verification result. Current plan envelope 2.1 names assessment_ref/selection_ref/planning_basis_ref; both selection and basis refs are included in the existing PLAN v2 decision_refs. The immutable closure binds assessed evidence, selected scope and changes since assessment. The service rejects a wrapper/closure mismatch, stale continuation or in-scope blockers before Gate 2. Canonical subject v2 serialization and existing golden vectors remain unchanged; a new assessment-derived plan vector demonstrates the existing reference mechanism. Old 1.0/2.0 plan envelopes are historical-readable and require successor checkpoint-linked planning/approval for current execution. Assessment artifact digests cannot satisfy kind=PLAN or be exchanged for implementation approval.

For plan envelope 2.1, the subject decision_refs must contain the exact selection_ref and planning_basis_ref; both resolve their schema IDs and same-project registered bytes before authorization. The basis must point to that selection/report and exact scope. Other decision refs retain their respective schema/meaning. Typed checkpoint validation never reconstructs refs from mutable UI state. An old subject can still be hashed/reviewed as history, but its lack of current checkpoint prerequisites blocks execution; no upgrade rewrites it.

## Execution closure and performance decision identities

Current SOURCE and PLAN subjects must include exactly one role=RUNNER binding with adapter_id=rewrotron-engine. Its manifest_ref resolves [execution-manifest.schema.json](../../specs/project/execution-manifest.schema.json); version equals engine_version and implementation_ref equals engine_binary_ref. The manifest pins executable bytes, build environment, dependency lock, canonicalizer and every consumed schema byte ref, capability IDs and qualified control refs. The build manifest includes Go/driver/SQLite/library/platform versions and build flags. Register installed trusted distribution/control evidence under the project; never replace it with an agent's assertion. Adapter bindings resolve manifest 2.2 for package-callable SOURCE/TARGET bindings or explicit built-in 2.1 registrations, exact implementation/schema bytes and applicable qualification records. Qualification refs resolve [qualification.schema.json](../../specs/adapters/qualification.schema.json), under SERVICE-CONTRACTS. The manifest's build/control artifact closure is retained with approval evidence; it has no back-reference to the subject, avoiding hash cycles.

PLAN decision_refs also includes exactly one typed [performance policy](../../specs/verification/performance-policy.schema.json), including an explicit evidenced not-applicable decision when performance is outside scope. Workload/method/threshold changes require successor approval. Policy and execution manifests are referenced immutable records, not new hash-preimage fields: canonical subject version 2.0 and existing golden vectors remain unchanged. New fixtures demonstrate these bindings. Existing subjects without the current prerequisites can be hashed and inspected as history but cannot authorize current execution. The service never tries an old schema branch to bypass a current-version requirement.

Reconstruction first loads original canonicalizer/schema bytes without trusting current registries. Resume then checks that the actually running engine matches the retained binding; matching a version string alone is insufficient. Missing/incompatible old binary, build or schema blocks execution. Importing a historical subject does not install or execute its binary automatically. An upgrade requires a successor execution closure and applicable new human gates (Gate 1 if source-analysis execution choices change; Gate 2 for changed implementation/verification choices). There is no retroactive reinterpretation of previously approved rules or results. Rule capability changes within a schema URI still change pinned schema bytes and qualification. Historical hashes stay unchanged.

## Review-2 identity closure

SOURCE's existing snapshot_ref binds snapshot 2.1, including filesystem semantic profile and credential admission/variant closure. Original content identity and transformed execution identity remain distinct. PLAN's existing resolved/model/execution schema refs bind resolution 2.1, evaluation-context/response/effect/witness contracts and positive consumption coverage. Hash preimage 2.0 and all historical vectors remain unchanged: new artifact refs produce successor subjects, not rewritten old approvals. A graph/schema/variant/profile change triggers currentness checks and applicable successor approval. Missing new prerequisites means historical-only, not automatic conversion. Execution witnesses are produced after launch and included in results/release closure; they cannot be fabricated as future Gate 2 evidence.

## Package binding closure

Package-callable bindings use adapter manifest 2.2 under SERVICE-CONTRACTS; explicitly registered built-in 2.1 bindings retain their exact qualification requirements. Consumed package.json descriptor and package-tree evidence refs are pinned in execution-manifest 1.1 package_refs for SOURCE and PLAN; PLAN additionally includes them and composed profile/qualification refs in its existing decision_refs. SOURCE has no decision_refs. Package-free built-in execution retains manifest 1.0. The engine validates each descriptor/content pair and complete consumed file closure before approval. A descriptor alone cannot reconstruct package bytes: retain the sorted rwt-skill-package-1 inventory and every consumed file, checking its root hash against the frozen package evidence rather than the current discovery index. Adapter manifests pin executable binding, operation schemas and qualifications. No canonical preimage/version change is made; historical subjects remain byte-identical. A successor binding/protocol/schema/profile/package requires new applicable qualification and human confirmation; imports never execute package hooks or binaries automatically.
