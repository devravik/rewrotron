# Compatibility and relation-preserving normalization

**Owner:** Required comparison dimensions, policy and verdict semantics. Comparison is bounded by approved corpus/profile/environment/resolution and exact captured evidence. [DIFFERENTIAL-TESTING](DIFFERENTIAL-TESTING.md) owns replay; [DATABASE-COMPARISON](DATABASE-COMPARISON.md) owns qualified state/reset.

Compare applicable status, ordered/multivalue headers, cookie attributes/lifecycle, redirect chains, raw bodies or approved semantic HTML/JSON, DB reads/writes/sequences/transactions, sessions/flash/cache/TTL, filesystem effects, queues/delivery/retry/ack, external effects, errors, authorization and logical identity relations. A dimension is required unless the approved contract demonstrates non-applicability. Semantic HTML comparison must declare DOM/text/form/link/attribute properties; JSON comparison uses [EVALUATION-CONTEXT](../02-domain/EVALUATION-CONTEXT.md) numeric projection, preserves exact integer/decimal tags and distinguishes absence/null/order. No “same-looking” binary/PDF acceptance without a format-specific approved comparator.

PASS requires complete sufficient evidence and every required assertion in the exact scope. Known violation is MISMATCH; missing/unsupported/conflicting evidence is UNKNOWN. Overall MISMATCH dominates UNKNOWN when a definite violation exists; neither is accepted. Intentional changes are separately reported approved policy obligations and cannot waive unknown evidence. Performance/adapter status is not a correctness verdict.

## Normalization rules

[normalization.schema.json](../../specs/verification/normalization.schema.json) requires exact path/type, variability class, relation group, lifecycle contract, business significance, immutable decision_ref and negative mutation evidence. decision_ref names a proposal hashed in Gate 2; the plan receipt approves it transitively. It is not a nonexistent future approval ID. Rule edits require successor policy/plan and invalidate results.

Generated IDs use a typed bijection between source/target logical entities across response/DB/foreign keys/URLs/effects, partitioned by actor/workflow/connection. Mappings cannot collapse distinct entities or mask broken relationships. UUID/sequence/token values may differ only within approved relations. CSRF/session normalization preserves issuance, principal binding, rotation, expiry, invalid/replayed-token rejection, logout and concurrent session behavior. Clock normalization controls the clock and tests business boundary conditions; refund timestamps cannot be dropped. Preserve ordering unless a reviewed contract states unordered semantics and a mutant changing meaningful order is rejected.

Repeated observations only propose variability. A broader normalizer must have independent evidence and required mutants showing wrong principal, wrong ID link, expired/replayed token, boundary-time decision, duplicate effect and deleted write still fail. No generic ignore-all-dynamic-fields policy. Comparator/tool upgrade and policy edits require current mutation controls and reapproval when semantics change. Unknown comparator behavior remains UNKNOWN.

Identity-map records use verification/identity-map.schema 2.1 and are execution evidence, not approved normalization choices. Service checks enforce per-group/actor/connection bijection and all referenced relationship assertions; ambiguous mapping yields UNKNOWN, wrong established relation MISMATCH. Typed exact integer/string values cannot be rounded by clients.

## Typed effects and delivery occurrences

[effect-payload.schema.json](../../specs/observation/effect-payload.schema.json) defines the narrow current DB/read/write/transaction, session, cache, file, queue/external and error payloads. [effect-occurrence.schema.json](../../specs/observation/effect-occurrence.schema.json) records logical effect ID, business key, destination, delivery attempt, retry-of, receipt/ack, phase, payload, side-local identity and causal occurrence. Effects 2.1 references ACTUAL_OBSERVED payload/occurrence refs; expected obligations use MODEL_EXPECTED in shadow contracts only. Unknown payload schema/capture is UNKNOWN/unsupported, never an empty match.

Compare destination, business identity, payload relationships, application effect cardinality and durable accepted outcomes. One logical message can have multiple transport attempts. Distinct receipt IDs do not themselves mean two business effects: a qualified sink must expose business application ID and applied-versus-deduplicated outcome. Repeated capture/stage records for one independently evidenced business_application_id describe one application, not separate applications. A sink must demonstrate unique application identity and durable outcomes; self-reused labels cannot hide multiple actual applications. One applied outcome plus retries returning the same durable acceptance can match a single obligation; two applied outcomes mismatch even with the same logical/idempotency label. Missing deduplication/application evidence is UNKNOWN. Accepted-before-ack crash requires receipt reconciliation before retry; an ACK without durable sink evidence cannot establish completion. The simulator/sink may implement transport behavior but cannot manufacture application emissions for the checker.

Principal comparisons use actual authentication/session/DB capture against the fixture intention and source outcome; actor labels are only selectors. HTTP cookies compare typed attributes/repetition and continuity; session rotation invalidates the old epoch where required. Pairwise identity maps preserve cross-dimension relationships and partition uniqueness. Non-UTF8 headers outside the supported request/response text profile are UNSUPPORTED, never lossy decoded. Known intentional security changes have their own approved obligations and difference report; they are not equivalent legacy behavior.

Async completion uses the minimum acknowledged logical-effect counter and fixed quiescence clock in [BEHAVIOR-MODEL](../02-domain/BEHAVIOR-MODEL.md). It does not compare effect cardinality by receipt count. Completion may be reached with extra receipts, but a second APPLIED business effect remains MISMATCH; unknown acceptance/ACK evidence cannot count toward completion. The existing delivery occurrence optionally records elapsed_ms; B4 timed completion requires it and qualified dispatch-anchor evidence. Omission retains untimed evidence but cannot establish a quiet interval.
